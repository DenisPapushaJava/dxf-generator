# Подготовка и публикация релиза

Все действия выполняются по явному запросу на выпуск. Обычная локальная разработка
не запускает Actions, сборку Windows и публикацию.

## Обычный CI

- Push в `main`: Linux desktop, ядро без Qt, Python-проверки упаковки/PE и независимый аудит DXF.
- Pull request: те же проверки и Windows со стандартным динамическим Qt.
- Изменения только Markdown, `docs/`, `design/` или `.vscode/` не запускают эти сборки.
- Рабочие ветки проверяются через PR, поэтому push ветки с открытым PR не создаёт второй запуск.
- Ручной `Build and test` позволяет включить Windows переключателем `windows`.

## Один ручной запуск для выпуска

1. Повысить `VERSION` в `CMakeLists.txt`. Перенести готовые изменения из
   `CHANGELOG.md` в раздел `## X.Y.Z` и проверить его описание. Уже выпущенную версию не использовать.
2. Сохранить исходники, лицензионные уведомления и описание одним commit; выполнить
   подходящие локальные проверки. Отправить изменения на GitHub на этапе согласованного выпуска.
3. По возможности дождаться успешного `Build and test` для этого commit.
4. В Actions открыть **Windows single EXE (manual)**, выбрать нужную ветку/тег и
   включить **prepare_release**. Значение по умолчанию `false` оставляет режим проверки
   EXE и сохранения временного артефакта без создания Release.
5. Workflow фиксирует SHA на момент запуска. Успешный CI на push или ручной CI **того же SHA**
   используется повторно. Результат PR не подставляется: там проверяется merge с основной веткой.
   Если подходящего результата нет, запускается тот же Linux workflow, параллельно
   со статической Windows-сборкой. Если CI ещё выполняется, возможна повторная Linux-проверка;
   шаг 3 позволяет её избежать. Динамическая Windows-сборка здесь не запускается.
6. Windows выполняет все CTest, включая реальную замену/откат EXE, PE-аудит и WinHTTP.
   Только после успеха сохраняются EXE и `build-info.json` с SHA, версией, Qt и суммой файла.
7. После успеха всех проверок отдельное задание скачивает полный Qt-архив,
   проверяет закреплённую SHA-256, упаковывает материалы и создаёт **черновик** Release.
   Затем сравнивает размеры и SHA-256 загруженных GitHub assets с локальными файлами.

Существующий Release или draft этой версии не перезаписывается. Существующий тег
допустим только если указывает на тот же commit. При частично загруженном draft
после ошибки сети сначала проверить его в Releases; повторный запуск намеренно
не заменяет его файлы автоматически.

## Что окажется в черновике

- `dxf-generator-windows-x64.exe` — единственный файл для обычного запуска, имя фиксировано контрактом обновления.
- `dxf-generator-vX.Y.Z-examples.zip` — примеры XLSX/CSV/TSV и памятка.
- `dxf-generator-vX.Y.Z-sources.zip` — точный commit приложения, QXlsx, полный Qt, лицензии и инструкции пересборки.
- `THIRD-PARTY-NOTICES.txt` — полные уведомления отдельно от встроенной справки.
- `build-info.json` — привязка EXE к commit, конфигурации Qt и проверкам.
- `SHA256SUMS.txt` — суммы всех перечисленных файлов.

Описание берётся из раздела текущей версии в `CHANGELOG.md`; сведения о размере,
исходниках и Windows-проверках добавляются автоматически. Исходники, EXE и будущий
тег относятся к одному SHA. Запись о конкретном артефакте больше не требует
отдельного commit документации перед установкой тега.

## Публикация

Открыть черновик в Releases, проверить описание и вложения. Проверка на чистой
Windows и в целевой CAD/CAM остаётся ручной. Нажать **Publish release** и выбрать
стабильный latest release. Workflow сам этого не делает; публикация не пересобирает EXE.

После публикации проверить `/releases/latest` и скачивание через код обновления.
`gh release edit vX.Y.Z --draft=false --latest` — эквивалентное отдельное действие
для согласованного выпуска через CLI, не часть подготовки черновика.

## Qt и кеш

Единый рецепт: `cmake/qt-static.json` — версия, commit, SHA-256 исходного архива
и параметры configure. Его используют оба Windows workflow и скрипты уведомлений/упаковки.
Ключ кеша учитывает рецепт и версию MSVC. SDK сохраняется сразу после сборки Qt,
до проверок приложения, поэтому их ошибка не теряет SDK.

Первый запуск с новым ключом один раз пересоберёт Qt; прежний ключ намеренно
не подставляется для потенциально другого компилятора/рецепта. После прогрева
SDK используется повторно. Скорость нового процесса измеряется при следующем
согласованном запуске Windows, не объявляется подтверждённой локальными тестами.

Скрипты используют Python standard library и Git; GitHub CLI требуется только
для обращения к Actions/Releases. Дополнительных библиотек приложения нет.
Сама упаковка `scripts/package_release.py` работает без сети с заранее переданным
Qt-архивом. Она требует чистый checkout и новый выходной каталог внутри `build/`.
